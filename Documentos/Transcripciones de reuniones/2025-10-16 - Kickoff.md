Luego un servicio de sincronización opcional que pueda comunicarse con el backend cuando esté disponible."

[00:01:53] Laura (UX): "¿Y eso afectaría a cómo el usuario ve sus datos? Porque si usamos almacenamiento local, ¿podría perderlo si cambia de dispositivo?"

[00:02:14] Elena: "Perfecto. Entonces, el MVP incluirá solo almacenamiento local. La sincronización sería parte de una segunda fase."

[00:02:26] David: "En ese caso necesito saber qué librerías o mecanismos de persistencia local vais a usar, para poder diseñar las pruebas. No es lo mismo testear SQLite en .NET que IndexedDB en Angular."

[00:02:39] Rafa: "Tranquilo, hablaremos de eso en la parte técnica. Pero la idea sería algo así: en el frontend Angular, usamos IndexedDB con un wrapper tipo ngx-indexed-db o incluso PouchDB. En el backend .NET, solo tendríamos endpoints preparados para sincronizar cuando toque. Eso nos da independencia."

[00:10:15] Laura: "Yo diría: el usuario puede crear su huerto, añadir macetas o áreas, colocar plantas y consultar información básica de cuidado. Sin registro ni sincronización."

[00:10:28] Rafa: "Correcto. Además, una vista principal tipo lienzo editable para diseñar el huerto, y una base de datos local con catálogo de plantas."

[00:10:39] David: "Y debemos tener un sistema de guardado automático, por si el usuario cierra la app. No quiero que se pierdan los datos entre sesiones."

[00:10:50] Elena: "Eso es parte del almacenamiento local, ¿no, Rafa?"

[00:10:54] Rafa: "Sí. Podemos guardar cada acción de usuario en IndexedDB y rehidratar el estado al iniciar. También podríamos tener una capa de persistencia en Angular con NgRx Store, sincronizado con IndexedDB, para tener estado reactivo y persistente."

[00:11:20] Laura: "Genial. Eso me permite diseñar un flujo sin necesidad de login inicial. Entrar → Crear huerto → Añadir planta → Ver cuidados. Simple y limpio."

(Todos asienten)

[00:11:40] Elena: "Perfecto. Entonces definimos como MVP:

Diseño visual del huerto.

Base local de plantas.

Información de cuidado.

Guardado local persistente.

Sincronización fuera del alcance."

[00:12:00] David: "Y yo añado: criterios de aceptación básicos, como carga de datos locales en menos de 2 segundos y no pérdida de datos al cerrar la app."

🧱 Fase 2 — Arquitectura técnica de alto nivel

[00:20:00] Rafa: "Vale, entremos en harina. A nivel técnico propongo una arquitectura Clean Architecture con separación clara de capas. En el backend C# .NET tendríamos:

Domain Layer: Entidades y lógica pura.

Application Layer: Casos de uso (commands y queries, siguiendo CQRS).

Infrastructure Layer: Implementación concreta, acceso a datos, repositorios.

API Layer: Endpoints expuestos vía REST."

[00:20:40] David: "¿Por qué REST y no GraphQL?"

[00:20:43] Rafa: "Por simplicidad en el MVP. GraphQL añade complejidad innecesaria si el backend solo sincroniza más adelante. REST es suficiente. Si en el futuro la sincronización crece, podemos agregar GraphQL o gRPC."

[00:21:00] Laura: "¿Y la comunicación entre frontend y backend sería sólo para sincronización? Porque ahora todo vive local."

[00:21:08] Rafa: "Exacto. Durante el MVP el backend sólo servirá para descargar el catálogo inicial de plantas, que actualizaremos cada X semanas. Así que solo habrá un endpoint público para eso."

[00:21:22] Elena: "Entonces ¿tenemos backend mínimo, casi estático?"

[00:21:25] Rafa: "Sí, básicamente. Pero la estructura debe permitir crecer sin reescribir. Por eso aplico arquitectura limpia, aunque de momento tengamos pocas capas activas."

[00:21:40] David: "¿Y qué base de datos usaríamos en el backend?"

[00:21:44] Rafa: "Probablemente PostgreSQL, por compatibilidad con contenedores y facilidad de uso en CI/CD. Aunque para el MVP, con datos estáticos, podríamos usar SQLite en modo servidor temporal."

[00:22:00] Elena: "Bien, me gusta que no complicamos de más. Y CI/CD, ¿qué propones?"

[00:22:07] Rafa: "GitHub Actions para integraciones automáticas. Cada commit en main lanza build, tests y despliegue a entorno de staging. En frontend, Angular con build optimizada y testing en Cypress + Jest. En backend, NUnit para unitarios y Postman/Newman para e2e de API."

[00:22:40] David: "Genial, puedo automatizar la suite con eso. Pero quiero que desde el principio haya pipelines de test configurados. No después."

[00:22:52] Rafa: "Totalmente. Sprint 0 incluirá configuración de CI/CD, linters, formato de código, y tests básicos."

(Laura sonríe mientras Rafa dibuja un esquema rápido en la pizarra virtual)
